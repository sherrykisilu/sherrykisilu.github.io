Killing a PostgreSQL primary on purpose

I deployed a three-unit PostgreSQL cluster with Juju on Kubernetes, deleted the primary, and watched what the operator did. The data survived, which I expected. How it survived taught me more.

At work I've spent time keeping services alive by hand: updating machines, nursing containers back after they fall over, recovering what went down. So I've been curious about the other approach, where the knowledge of how to run a system lives in software instead of in someone's head. Database operators promise exactly that. I wanted to see one handle the worst ordinary day a database has: losing its primary.

The short version, for anyone new to this

Think of a busy kitchen. In a stateless system any chef can take any order: if one goes home, another steps in and nothing is lost. A database is stateful: each chef keeps a notebook of orders. If a chef leaves, you can't just hire any replacement. Someone has to come back to the same station, with the same notebook, and everyone has to agree on who is now in charge of new orders.

Kubernetes is good at the first part: it brings a replacement back to the same station with the same notebook. Deciding who is in charge, and in what order to do things so no orders get lost, is the job of the operator.

The setup

  • An Ubuntu 24.04 VM on Multipass, provisioned with a cloud-init file that installs MicroK8s, Juju and the rest.
  • A Juju controller bootstrapped onto MicroK8s.
  • juju deploy postgresql-k8s --channel 16/stable --trust -n 3: Canonical's Charmed PostgreSQL, three units, one primary and two replicas.
  • Credentials issued through an integration rather than by hand: juju integrate data-integrator postgresql-k8s. The charm created a database and a user for me. I didn't write a line of SQL to get them.

Before breaking anything, I wrote 100 rows through the primary. The test table records which server answered each write, so I could see where my writes landed before and after.

The experiment

$ kubectl -n pg delete pod postgresql-k8s-0     # the current primary

What I learned

1. The old primary came back as a replica, and that's the point

By the time unit 0's pod restarted, the cluster had already moved on: unit 2 had been promoted and was accepting writes. If unit 0 had come back insisting it was still the primary, there would have been two primaries with different data. That's split-brain, one of the worst things that can happen to a database. So it rejoined as a replica and caught up from the new primary. Keeping its identity didn't mean keeping its role.

2. Same name, same storage, new address

The recreated pod kept its name, postgresql-k8s-0, and its volumes, but got a new IP address. Each unit has four persistent volume claims: data, archive (the write-ahead log, used for replication and point-in-time recovery), logs and temp. Their ages showed they had outlived the pod. That's why nothing was lost.

3. Clients follow a label, not a machine

My writes went to a Service called postgresql-k8s-primary. Its selector is role=primary. When unit 2 was promoted, the label moved, and the Service followed it. My client never needed to know the failover happened. That's transparency in the distributed-systems sense: the complexity is still there, but the user doesn't have to carry it.

4. The operator runs beside the database

Each PostgreSQL pod runs two containers: postgresql and charm. The operator isn't a distant controller; it sits next to the thing it manages.

What I couldn't measure yet

I wanted a failover time, and I don't have an honest one. My first write after deleting the pod succeeded instantly, but it was answered by the old primary before its pod had finished shutting down, so it measured nothing. Juju's status display also refreshes on a timer, so "when Juju showed the new primary" was minutes after the promotion really happened. Measuring it properly means polling each unit's pg_is_in_recovery() directly. That's the next experiment.

What this would have cost by hand

Without an operator, someone would have had to notice the primary was dead, choose the most up-to-date replica, promote it, point every application at it, and later rebuild the failed node as a replica. Writes would fail for that whole window, and a rushed choice under pressure (promoting a replica that was behind) could lose data. In the lab, all of that happened while I was reading the output.

Next

  • Measure failover time properly.
  • Back up to S3-compatible storage and, more importantly, restore. A backup you haven't restored is a hope, not a backup.
  • Repeat it on plain VMs with the machine charm.
